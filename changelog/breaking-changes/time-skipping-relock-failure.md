`WorkflowEnvironment.getResult` (and `executeWorkflow` and the other `getResult*` and `executeWorkflow*` variants) on the time-skipping server now returns `error.TimeLockLost` when it can't unlock time skipping or lock it again after the wait, and marks the environment unusable: its `startWorkflow*`, `signalWorkflow`, `queryWorkflow`, `updateWorkflow`, `signalWithStartWorkflow`, `updateWithStartWorkflow`, `getResult*`, `executeWorkflow*`, `sleep` and `now` then return `error.TimeLockLost`. Before, the failed call's error was returned and the environment carried on with time skipping unlocked, so a later workflow waiting on a signal or an update skipped straight to its timeout. A `switch` over these methods' errors needs a `TimeLockLost` prong; start a new environment when it is returned.
