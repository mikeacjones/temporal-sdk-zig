# Changelog

All notable changes to this project are documented in this file, one section per release, newest first. The project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html) as described in [docs/releasing.md](docs/releasing.md), and [docs/upgrading.md](docs/upgrading.md) shows how to move code across releases with breaking changes.

This file holds completed releases only. Changes that haven't been released yet are fragments under [changelog/](changelog/README.md); `scripts/changelog-assemble.sh` turns them into a release's section when the release is prepared.

## [0.1.0-alpha.1] - 2026-11-18

Requires Zig 0.17.1. Built against sdk-core v1.2.0.

### Added

- `activity.Def` defines an activity from a function taking `*activity.Context`; `activity.defs` defines one per method of a struct whose state the activities share, registered with `Worker.registerActivities`.
- `activity.Context` gives an activity its allocator, its worker's `std.Io`, `info()`, a logger, a client, headers, propagated values and metrics.
- `activity.Context.heartbeat` and `heartbeatDetails` record progress for retries, and a cancel from the workflow, a timeout or worker shutdown reaches the activity as `error.Canceled` with `cancelReason()` saying why.
- `activity.Context.fail` sets the failure's type, details, retryability, category and next retry delay; `completeAsync` leaves the activity to be completed through a client.
- `activity.DynamicDef` defines an activity that runs every type the worker has no `Def` for.
- `activity.Info` carries the activity's `schedule_to_close_timeout`, `start_to_close_timeout`, `heartbeat_timeout`, `retry_policy` and `priority`, and `Info.deadline()` says when the current attempt times out.
- `activity.Context.isWorkerStopping` and `waitForWorkerStop` tell an activity its worker has begun stopping, so it can finish or save progress within `worker.Options.graceful_shutdown_period`.
- `testing.ActivityEnvironment.cancel` cancels the running activity with a reason, and `stopWorker` fires the worker-stop signal; `executeActivity` now takes the environment by pointer, so declare it with `var`.
- `workflow.ChildWorkflowOptions.priority` gives a child workflow a priority key and fairness key and weight; null or zero fields inherit the parent's.
- `workflow.ChildWorkflowCancellationType.wait_cancellation_requested` reports a child's cancellation once the server has recorded the request, without waiting for the child to close. Canceling a workflow cancels only the children a coroutine is waiting on; the others are left to their `parent_close_policy`.
- `Client.executeActivity` runs a standalone activity with no workflow and returns a `client.ActivityHandle` to wait for, describe, cancel or terminate it; `Client.listActivities` and `Client.countActivities` find them.
- `Client.completeActivity`, `failActivity`, `recordActivityHeartbeat` and `reportActivityCancellation`, each with a `ById` variant, finish an activity that returned `activity.Context.completeAsync` from any process.
- `Client.cancelWorkflowWithOptions` requests cancellation with `client.CancelOptions`: a `first_execution_run_id` that limits it to the chain of runs that started with that run, and `links` recorded on the cancel-requested event. `client.TerminateOptions` gains `links`, recorded on the terminated event.
- `client.Client.connect` connects to a server and namespace with `client.Options`: address, TLS and mutual TLS, API key, headers, gRPC retry policy, `rpc_timeout`, codecs, interceptors and metrics. `Client.checkHealth` checks the connection.
- `client.loadOptions` and `client.loadDefaultOptions` read connection settings from a Temporal config file profile and `TEMPORAL_*` environment variables.
- `Client.updateApiKey`, `Client.updateHeaders` and `Client.reconnect` change a connected client's credentials, headers or connection.
- `Client.forNamespace` returns a client for another namespace of the same server that shares the existing client's connection and sdk-core runtime, so a program working in several namespaces connects once. The clients may be closed in any order, and the last to close frees the connection and runtime; `reconnect`, `updateApiKey`, and `updateHeaders` on any of them apply to all and move every worker running on them. See [Connecting](https://github.com/mikeacjones/temporal-sdk-zig#connecting).
- `client.Client.init` creates a client that connects on first use, so a process can build its client before the server is reachable: the first call that needs the server connects, calls made together share one attempt, and each gives up after its own `client.Options.rpc_timeout` or when its task is canceled; a connection that fails is logged and tried again by the next call, and `Client.ensureConnected` connects explicitly. `Client.currentConnection` now connects first and returns `client.ConnectError!bridge.Connection`, `Client.updateApiKey` returns `error{OutOfMemory}!void`, `worker.Worker.RunError` gains `ConnectFailed`, and `Client.connect` and `Client.reconnect` reject invalid header names and values with `error.InvalidOptions`. See [Connecting](https://github.com/mikeacjones/temporal-sdk-zig#connecting), which now also documents rotating the API key and headers with `Client.updateApiKey` and `Client.updateHeaders`.
- `Client.signalWorkflowByName`, `Client.updateWorkflowByName`, `Client.signalWithStartWorkflowByName` and `Client.updateWithStartWorkflowByName` send a signal or an update whose name is known only at run time, with the arguments as a tuple, to a workflow's handler for that name or its dynamic handler; the update calls return a `client.WorkflowUpdateHandle` that decodes the result as the type the caller gives. See [Signals, queries, and updates](https://github.com/mikeacjones/temporal-sdk-zig#signals-queries-and-updates).
- `client.Options.http_connect_proxy` connects through an HTTP CONNECT proxy, with optional basic auth; `client.Options.keep_alive` sets the gRPC keep-alive pings, or turns them off; and `client.Options.worker_heartbeat_interval` sets how often workers heartbeat to the server, or turns heartbeats off. See [Proxy, keep-alive, and worker heartbeats](https://github.com/mikeacjones/temporal-sdk-zig/blob/main/README.md#proxy-keep-alive-and-worker-heartbeats).
- `Client.terminateWorkflowWithOptions` records details in the terminated event and, with `client.TerminateOptions.first_execution_run_id`, terminates only the chain of runs that started with that run.
- `Client.resetWorkflow` resets a workflow to the end of an earlier workflow task in a new run, with `client.ResetOptions` choosing which later signals, updates, and Nexus events are not reapplied.
- `Client.updateWorkflowExecutionOptions` sets or removes a running workflow's versioning override and returns its `client.WorkflowExecutionOptions`.
- `Client.withRpcOptions` returns a view of a client whose calls send their own deadline and extra gRPC metadata (`client.RpcOptions`: `timeout`, `metadata`, `binary_metadata`) without changing `client.Options`; the timeout replaces `Options.rpc_timeout` for those calls, and the metadata is merged with `Options.headers`, the view's value winning. See [Connecting](https://github.com/mikeacjones/temporal-sdk-zig#connecting).
- `Client.createSchedule` creates a schedule from a `schedule.Schedule` (calendar, interval or cron specs) and returns a `client.ScheduleHandle` that describes, updates, pauses, triggers, backfills and deletes it; `Client.getScheduleHandle` and `Client.listSchedules` find existing ones.
- `Client.callService` calls any method of the workflow, operator, cloud, test, and health services with the method's generated request and response types, which `client.ServiceRequest` and `client.ServiceResponse` name; a refused call returns a `client.CallServiceError` named after its gRPC status, and `client.RpcFailure` gives the status with its `temporal.api.errordetails.v1` details. Namespaces are registered, described, updated, and listed this way. See [Namespaces and raw service access](https://github.com/mikeacjones/temporal-sdk-zig#namespaces-and-raw-service-access).
- `client.RpcOptions.retry` sets, for the calls of a view from `Client.withRpcOptions`, whether sdk-core retries them with the connection's retry policy.
- `temporal.proto` includes the Cloud Operations API's types (`temporal.proto.temporal.api.cloud`).
- `Client.executeWorkflow` and `Client.executeWorkflowByName` start a workflow with `client.StartWorkflowOptions` (ID, task queue, timeouts, ID reuse and conflict policies, retry policy, cron schedule, memo, search attributes, priority, start delay, eager start) and return a `client.WorkflowRun` whose `get` follows continue-as-new to the result; `Client.getWorkflow` makes a handle to an existing run.
- `Client.signalWorkflow`, `Client.queryWorkflow`, `Client.updateWorkflow`, `Client.signalWithStartWorkflow` and `Client.updateWithStartWorkflow` send typed messages declared with `workflow.SignalDef`, `workflow.QueryDef` and `workflow.UpdateDef`, or by name; update handles wait for a chosen stage.
- `Client.describeWorkflow`, `Client.fetchHistory`, `Client.historyIterator`, `Client.listWorkflows`, `Client.countWorkflows`, `Client.cancelWorkflow` and `Client.terminateWorkflow` inspect and manage runs.
- A type may declare `toPayloadWithContext` and `fromPayloadWithContext` to receive a `converter.Context` (namespace, workflow ID and type, activity type and ID, propagated values) for the call its value belongs to; the SDK passes it for client, workflow, activity, child workflow and standalone activity conversions, and `converter.toPayloadWithContext`, `converter.fromPayloadWithContext`, `EncodedValues.withContext` and the `converterContext()` accessors on workflow and activity contexts and futures pass it for failure details. See [Payloads](https://github.com/mikeacjones/temporal-sdk-zig/blob/main/README.md#payloads).
- `converter.toPayload` and `converter.fromPayload` encode and decode arguments, results and details as JSON, plain bytes (`converter.Bytes`), null, protobuf messages (ProtoJSON or `converter.ProtoBinary`) and `converter.Time`; `converter.EncodedValue` and `converter.EncodedValues` decode payloads lazily.
- `converter.PayloadCodec`, set with `client.Options.codecs`, transforms every payload the client and its workers send, with `converter.ZlibCodec` for compression and a `converter.Context` for each call; `converter.codecHandler` serves a codec to the Web UI and CLI.
- Failures carry a message, type, details and cause chain, read from the future or handle after a Zig error such as `error.ActivityFailed` or `error.WorkflowFailed`.
- Deadlock detection: workflow code that runs longer than `worker.Options.deadlock_detection_timeout` (2 seconds by default; null turns it off) without returning to the workflow scheduler fails its workflow task with a `WorkflowDeadlockDetected` failure, is logged, and its run is evicted to replay from history; the workflow itself doesn't fail. `testing.WorkflowReplayer.Options.deadlock_detection_timeout` applies the same limit during replay. See [Deadlock detection](https://github.com/mikeacjones/temporal-sdk-zig#deadlock-detection).
- `failure.Application.cause` puts a failure under the one `ctx.fail` (in workflows, activities and Nexus operations) or `Client.failActivity` sends, such as a future's failure; the whole chain reaches the server.
- `failure.kind` reads a failure as `failure.Kind`, a tagged union with one case per failure kind, with details as `converter.EncodedValues`, durations as `std.Io.Duration`, and timeout types and retry states as Zig enums.
- `client.Options.failure_converter` (also on `testing.WorkflowEnvironment.Options` and `testing.WorkflowReplayer.Options`) takes a `converter.FailureConverter` whose `toFailure` transforms each failure user code sends (workflow, activity, local activity, Nexus handler and update rejection failures, query failures, `Client.failActivity`) and whose `fromFailure` transforms each failure user code reads (in a workflow and on a client), with the call's `converter.Context`. See [Failures](https://github.com/mikeacjones/temporal-sdk-zig/blob/main/README.md#failures-1).
- `client.Options.encode_failure_attributes` moves the message and stack trace of each failure the client and its workers send into `encoded_attributes`, before the payload codecs run, in the format other Temporal SDKs use; received failures are always decoded back.
- Failures the worker builds from an error a workflow, signal or update handler, or activity returned carry the error's return trace in `stack_trace`, in builds with error return tracing (Debug, and ReleaseSafe when the program's root module sets `.error_tracing = true`); `worker.Options.failure_stack_traces = false` turns it off.
- The SDK is a Zig package built on Temporal's Rust Core SDK (sdk-core), for Zig 0.17.1. A release tarball fetched with `zig fetch --save` links a prebuilt core library for `aarch64-macos`, `x86_64-macos`, `aarch64-linux-gnu`, `x86_64-linux-gnu`, `aarch64-linux-musl` and `x86_64-linux-musl`, so it needs no Rust toolchain; a recursive clone builds the core from source with cargo.
- Context propagators (`client.Options.propagators`) now apply to Nexus operations: a workflow's propagated values travel in the `temporal-zig-context` Nexus header of each operation it calls, the handler reads them with `nexus.Context.propagated`, and a workflow a workflow-run operation starts carries them on. See [Context propagation](https://github.com/mikeacjones/temporal-sdk-zig#context-propagation).
- `interceptor.WorkflowOutbound.executeNexusOperation` intercepts the Nexus operations a workflow calls, and `interceptor.Worker.interceptNexusOperation` hands out `NexusOperationInbound` and `NexusOperationOutbound` interceptors around the start and cancel of each operation a worker handles and around its handler's logger.
- `nexus.OperationDef` and `nexus.ServiceDef` define a Nexus service contract, `nexus.ServiceHandler` binds each operation to a synchronous handler or to a workflow-run handler that returns a `nexus.WorkflowStart`, and `Worker.registerNexusService` registers it; handlers get a `nexus.Context` and fail with `ctx.fail`, `ctx.failCanceled` or `ctx.handlerError`.
- `ctx.logger()` returns a structured `log.Logger` carrying the workflow's or activity's context; records go to a `log.Sink` set with `client.Options.logger` or `worker.Options.logger`, which also receives sdk-core's logs.
- `client.Options.metrics` exports the SDK's and sdk-core's metrics to Prometheus, an OpenTelemetry collector or a custom `metrics.Handler`, and code records its own through `ctx.metrics()` and `client.metrics()`.
- `interceptor.Worker` and `interceptor.Client` intercept workflow, activity and client calls, installed with `worker.Options.interceptors`, `client.Options.worker_interceptors` and `client.Options.interceptors`.
- `propagation.ContextPropagator` carries values such as a tenant or trace ID through workflow, activity and child workflow headers.
- `temporal.protojson.encode` and `temporal.protojson.decode` write and read any generated protobuf message as ProtoJSON, as the Temporal CLI, Web UI and codec servers do: oneof fields flat, bytes and `map<string, bytes>` values as base64, and enums accepted by full name, short name (`WorkflowExecutionStarted`) or number.
- Each release's notes list breaking changes first, each saying what to do, and the [upgrade guide](https://github.com/mikeacjones/temporal-sdk-zig/blob/main/docs/upgrading.md) gives the before and after code for releases with breaking changes.
- `workflow.Context.createSession`, `recreateSession` and `completeSession` run a group of activities on one worker host; `worker.Options.sessions` makes a worker a session host.
- Workers answer the `__stack_trace` query that Temporal's UI and CLI send, for every workflow and with no registration: one entry per live coroutine (the workflow function, running signal and update handlers, and coroutines the workflow started) saying what it waits on and its call sites in workflow code. `workflow.StackTraceQuery` sends it from a client, and a handler the workflow registers for `__stack_trace` answers instead. See [Stack trace query](https://github.com/mikeacjones/temporal-sdk-zig#stack-trace-query).
- `client.StartActivityOptions` takes a `start_delay`, a `priority` and a `summary` for a standalone activity, `ActivityHandle.started` says whether `Client.executeActivity` started a new activity or returned the one already running, `ActivityHandle.pause`, `unpause` and `delete` pause, resume and delete it, and `ActivityDescription` reports the start delay, priority, summary and the latest heartbeat's details (`heartbeat_details`, decoded through the client's codecs). See [Standalone activities](https://github.com/mikeacjones/temporal-sdk-zig#standalone-activities).
- The `test-server-version` build option (`.test_server_version` in `b.dependency`'s arguments) sets the time-skipping test server release that `testing.TestServer` and `WorkflowEnvironment.startTimeSkipping` download, such as `"v1.40.0"`; it stays `"default"`, the release sdk-core picks, unless set.
- `testing.ActivityEnvironment.logger` takes a `log.Sink` that receives what the activity logs through `ctx.logger()`, with the context fields a worker adds, so a test can read or silence the activity's logs. See [Activity environment](https://github.com/mikeacjones/temporal-sdk-zig#activity-environment).
- `testing.WorkflowEnvironment.fromClient` makes a workflow environment on a server the test already runs, through a `client.Client` it has: it starts and stops no server and leaves the client open. See [Workflow environment](https://github.com/mikeacjones/temporal-sdk-zig#workflow-environment).
- `testing.createNexusEndpoint` creates a Nexus endpoint through any client, for a server that has no `testing.WorkflowEnvironment`, such as a `testing.DevServer` started with `--namespace` arguments for a handler in another namespace.
- `testing.WorkflowReplayer.replayListedWorkflows` replays every workflow run a visibility query lists, fetching each run's history through a client and returning a result per run. See [Replaying histories](https://github.com/mikeacjones/temporal-sdk-zig#replaying-histories).
- `testing.WorkflowEnvironment.startTimeSkippingWithOptions` starts the time-skipping environment with the client options `startWithOptions` takes (codecs, a logger, propagators, interceptors, metrics); `dev_server_extra_args` there returns `error.InvalidOptions`.
- `testing.WorkflowEnvironment.getResultWithOptions` and `getResultByNameWithOptions` take `client.WorkflowRun.GetOptions`, so a test can stop at one run of a continue-as-new chain (`.follow_runs = false` returns `error.WorkflowContinuedAsNew`) and still have time skipped and the run replayed.
- `testing.WorkflowEnvironment` runs workflows against a local dev server, with activity doubles and signal, query and update helpers; `WorkflowEnvironment.startTimeSkipping` uses the time-skipping test server.
- `testing.ActivityEnvironment` runs an activity function without a server.
- `testing.WorkflowReplayer` replays recorded histories, from JSON, files, a client or an iterator, to catch nondeterministic changes, one result per history.
- `testing.DevServer` and `testing.TestServer` start a local Temporal dev server or time-skipping test server.
- `Client.workerDeployment` and `Client.listWorkerDeployments` manage Worker Deployments: describe them and set the current or ramping version, version metadata and manager identity; `StartWorkflowOptions.versioning_override` pins a workflow to a version.
- Workers serve their registered Nexus services: a worker with a service polls its task queue for Nexus tasks, so a workflow can call a Zig handler through a Nexus endpoint, and a worker with only Nexus services runs. `worker.Options.max_concurrent_nexus_task_executions` and `max_concurrent_nexus_task_pollers` bound the requests handled and the polls open at once.
- `testing.WorkflowEnvironment.registerNexusService` and `registerNexusServiceWith` register a Nexus service on a test environment's worker.
- A Nexus workflow-run operation whose workflow start or cancel the server rejects fails by the rejection's gRPC status and carries the server's message: an invalid argument, for example, is a `bad_request` handler error that isn't retried.
- `worker.Options` gains `sticky_schedule_to_start_timeout`, `max_activities_per_second`, `max_task_queue_activities_per_second`, `default_heartbeat_throttle_interval`, `max_heartbeat_throttle_interval`, `max_eager_activity_reservations_per_workflow_task` (0 turns eager activities off) and `max_concurrent_local_activity_executions`; `run` returns `error.InvalidOptions` for a rate or duration out of range. See [Workers](https://github.com/mikeacjones/temporal-sdk-zig#workers).
- `worker.Options.poll_activity_tasks = false` stops a worker polling its task queue for activity tasks, so its activities run only as local activities of its own workflows.
- `worker.Options.workflow_task_poller_behavior`, `activity_task_poller_behavior` and `nexus_task_poller_behavior` take a `worker.PollerBehavior`: a simple maximum of open polls, or autoscaling between a minimum and a maximum from an initial count, following the server's feedback. `worker.Options.nonsticky_to_sticky_poll_ratio` sets the share of workflow task pollers that poll the task queue rather than the worker's sticky queue. Invalid settings make `Worker.run` return `error.InvalidOptions`. See [Poller behavior](https://github.com/mikeacjones/temporal-sdk-zig#poller-behavior).
- `worker.Worker` polls one task queue and runs the workflows and activities registered on it; `Worker.run` runs until `Worker.stop`, `Worker.runUntilSignal` until SIGINT or SIGTERM, and `Worker.waitUntilRunning` waits for polling to start. `run` returns an error when the worker can't start or polling fails fatally.
- `worker.Options` sets concurrency limits, pollers, the workflow cache size, identity, the graceful shutdown period, logging, interceptors, and a per-run `workflow_memory_limit`; workflow activations of different runs are processed in parallel.
- `worker.Options.deployment` makes a worker a version of a Worker Deployment, with `workflow.VersioningBehavior` keeping each run on its version or moving it to the current one; `build_id` and `use_build_id_versioning` cover build-ID versioning.
- `workflow.Context.executeActivity` and `executeLocalActivity` schedule activities with `workflow.ActivityOptions` and `workflow.LocalActivityOptions` (timeouts, retry policy, cancellation type, summary, priority, versioning intent) and return a `workflow.ActivityFuture`; `executeActivityByName` calls an activity by its type name.
- `workflow.ChildWorkflowOptions.static_summary` and `static_details` describe a child workflow; the UI and CLI show them on its started event. See [Child workflows](https://github.com/mikeacjones/temporal-sdk-zig#child-workflows).
- `workflow.Context.executeChildWorkflow` starts a child workflow and returns a `workflow.ChildWorkflowFuture` for its start and result, which can also signal and cancel it.
- `ctx.signalExternalWorkflow` and `ctx.cancelExternalWorkflow` signal or cancel another workflow by ID.
- Returning `ctx.continueAsNew` continues the workflow as a new run; `ctx.continueAsNewSuggested`, `historyLength` and `historySizeBytes` say when to.
- `workflow.Context.continueAsNewByName` continues as new under a workflow type named at run time, with the arguments as a tuple and the same `ContinueAsNewOptions`; a dynamic workflow passes `ctx.info().workflow_type` to continue under the type it runs as. See [Continue-as-new](https://github.com/mikeacjones/temporal-sdk-zig#continue-as-new).
- `workflow.Context.setCoroutineName` names the calling workflow coroutine for stack-trace queries, and `workflow.Context.coroutineName` reads it back.
- `std.Io.Semaphore`, `std.Io.Event` and `std.Io.Condition` are tested and documented on the workflow `std.Io`, with the field-plus-`Event` idiom for a value one coroutine sets and another waits for, and `std.Io.Select` cases that receive from a `std.Io.Queue`; see [Concurrency](https://github.com/mikeacjones/temporal-sdk-zig#concurrency).
- `workflow.Def` and `workflow.DefWithOptions` define a workflow from a function taking `*workflow.Context` or from a struct whose fields are the run's state; arguments and results are typed from the signature, and a bad signature is a compile error.
- Workflow code runs on a deterministic `std.Io` from `ctx.io()`: `io.sleep` is a durable timer, `io.now` workflow time, `io.random` seeded from the run, and `io.async`, `std.Io.Select`, `std.Io.Group`, `std.Io.Mutex` and `std.Io.Queue` run coroutines one at a time in a fixed order.
- `ctx.await` and `ctx.awaitTimeout` wait for a condition; canceling a coroutine cancels the timer, activity or child workflow it waits on.
- `workflow.DynamicDef` defines a workflow that runs every type the worker has no `Def` for.
- `workflow.Context.setDynamicQueryHandler` answers every query that has no handler of its own, with the query type and its arguments still encoded (`converter.EncodedValues`); see [Signals, queries, and updates](https://github.com/mikeacjones/temporal-sdk-zig#signals-queries-and-updates-1).
- `workflow.Context.setDynamicUpdateHandler` and `setDynamicUpdateHandlerWithValidator` handle every update that has no handler of its own, with the update name and its arguments still encoded (`converter.EncodedValues`), in a coroutine of its own; see [Signals, queries, and updates](https://github.com/mikeacjones/temporal-sdk-zig#signals-queries-and-updates-1).
- A workflow that completes, is canceled or continues as new while signal or update handlers are still running logs one warning naming them; a handler opts out with `workflow.HandlerOptions{ .unfinished_policy = .abandon }`, passed to the new `setSignalHandlerWithOptions`, `setUpdateHandlerWithOptions` and their by-name and dynamic variants, or at the end of a struct workflow's `signals` or `updates` entry.
- `workflow.Context.failWith` fails a workflow (or rejects an update) with a failure you already have, such as an activity's from `future.failure()`, so cleanup activities that fail afterwards on the error path no longer replace the workflow's failure. See [Failures](https://github.com/mikeacjones/temporal-sdk-zig#failures).
- Failure policy: `worker.Options.workflow_task_failure_errors` and `workflow.DefOptions.task_failure_errors` list errors that fail the workflow task instead of the workflow when the workflow function, a signal handler, or an update handler returns them; the run stays open and completes once code that no longer returns the error takes the retried task. `worker.Options.nondeterminism_fails_workflow` and `workflow.DefOptions.nondeterminism_fails_workflow` fail the workflow instead of its task on nondeterminism, `workflow.DynamicDefWithOptions` gives a dynamic workflow its own list, and `testing.WorkflowReplayer.Options.workflow_task_failure_errors` replays with the worker's list. See [Failure policy](https://github.com/mikeacjones/temporal-sdk-zig#failure-policy).
- Workflows handle signals, queries and updates with typed handlers, as declarations on a struct workflow or through `ctx.setSignalHandler`, `setQueryHandler`, `setUpdateHandler` and `setUpdateHandlerWithValidator`; `setSignalHandlerByName` and `setDynamicSignalHandler` handle signals named at run time, and `workflow.Context.allHandlersFinished` waits for running handlers.
- `workflow.Context.executeNexusOperation` and `executeNexusOperationByName` call a Nexus operation through an endpoint and return a `workflow.NexusOperationFuture` for its start, result and cancellation, with `workflow.NexusOperationOptions` for timeouts, headers and the cancellation type; `testing.WorkflowEnvironment.createNexusEndpoint` creates an endpoint on the dev server for tests.
- `workflow.Context.randomUuid` returns a random (version 4) UUID as text, drawn from the run's seeded randomness, so a replay gets the same values in the same order; use it for child workflow IDs or activity arguments. See [Determinism](https://github.com/mikeacjones/temporal-sdk-zig#determinism).
- `workflow.Context.signalChannel` and `signalChannelByName` return a `workflow.SignalChannel` that takes the place of a signal's handler, with `receive` (usable as a `std.Io.Select` case), `tryReceive` and `len`; see [Signals, queries, and updates](https://github.com/mikeacjones/temporal-sdk-zig#signals-queries-and-updates-1).
- `workflow.Context.removeSignalHandler`, `removeSignalHandlerByName` and `removeDynamicSignalHandler` unregister a signal handler or channel, and `workflow.Context.unhandledSignalNames` lists the signals nothing has taken, including those unread in a channel; the warning logged when a workflow finishes with such signals now counts unread channel signals too.
- `workflow.Context.sleep` blocks on a durable timer like `ctx.io().sleep`, with `workflow.SleepOptions.summary` shown by the UI and CLI on the timer's started event; run it as a coroutine to race or cancel it. See [Timers and conditions](https://github.com/mikeacjones/temporal-sdk-zig#timers-and-conditions).
- `ctx.patched`, `ctx.deprecatePatch` and `ctx.getVersion` keep old and new workflow code paths while runs on the old one remain.
- `ctx.sideEffect` records a nondeterministic value once; `ctx.upsertMemo`, `memoValue` and typed search attributes from `search_attributes.key` read and update the memo and search attributes.
- `ctx.info()`, `ctx.isReplaying()`, `ctx.lastCompletionResult` and `ctx.previousRunFailure()` describe the run, including cron and retried runs.

### Changed

- Building the core from source finds `cargo` in rustup's install directory (`$CARGO_HOME/bin`, default `~/.cargo/bin`) when it isn't on `PATH`, as in a non-login shell.
- The workflow task failure sent when workflow code returns `error.OutOfMemory` now has the application failure type `OutOfMemory` instead of `UnsupportedJob`.
- [PARITY.md](https://github.com/mikeacjones/temporal-sdk-zig/blob/main/PARITY.md)'s feature table now names the tracking issue for every partial or missing feature, marks the GA features deferred past the first release as `GA, deferred` and lists them apart from those the first release still needs, and shows the dynamic query and update handlers, read-only query handlers and update validators, and the warning for unfinished handlers as supported.
- Query handlers and update validators must not change workflow state, and the SDK now enforces what it can intercept: a call from one that would start an activity, timer, child workflow or other command, register or remove a handler, take a signal from a channel, start a coroutine, or block is refused, and the query fails, or the update is rejected, with a `ReadOnlyViolation` failure naming the call; so does waking a workflow coroutine through `std.Io` (`Event.set`, `Condition.signal`, `Queue.put`, `Mutex.unlock`), though the wake itself still happens. Nothing is sent and the workflow task doesn't fail; before, such a call could send a command from a query or a validator, or crash the worker. Changes a handler makes to workflow data or to a `std.Io` primitive can't be undone. In a query handler, `workflow.Context.allocator` now returns the query's memory, freed once the answer is sent, and `Context.fail` describes the query's failure or the update's rejection instead of the workflow's.

### Deprecated

- `converter.CodecContext` is now `converter.Context`, the one context of payload codecs and a type's payload hooks; the old name remains as an alias.

### Fixed

- An activity's cancellation is no longer lost when it arrives while something on the activity's task waits on its `std.Io` without returning the error to the activity: the SDK's own work for the activity (decoding its input and arguments, `activity.Context.heartbeat` and its payload codecs, `activity.Context.heartbeatDetails`), or an allocation from `activity.Context.allocator`, which in a Debug build on macOS waits for std's debug info lock when `std.testing.allocator` or `std.heap.DebugAllocator` captures its stack trace. The activity's next wait on `ctx.io()` now returns `error.Canceled`; before, the activity kept running until its timeout, and stopping its worker waited for it.
- A worker ends an activity attempt that returns `error.Canceled` after the activity was paused or reset as a retryable `ActivityPause` or `ActivityReset` failure, which the server accepts, instead of reporting it canceled, which the server refused; a cancel requested before that attempt ends still ends the activity canceled, and the attempt's last heartbeat details are kept. A standalone activity's logs no longer carry empty `WorkflowType`, `WorkflowID` and `RunID` fields.
- A workflow or update that fails is no longer reported as a potential deadlock when reading debug info for its failure's stack trace takes longer than `worker.Options.deadlock_detection_timeout`: that time is SDK work and is not counted, like the stack trace query's.
- `history.fromJson` base64-decodes every `Payload.metadata` value, including values that are not text, which it used to leave as base64; a metadata value that is not valid base64 now fails with `error.InvalidHistoryJson` instead of being kept as text.
- `json/protobuf` payloads now decode enums written by short name, and base64-decode the values of `map<string, bytes>` fields such as `Payload.metadata` in the messages they hold, instead of leaving them as base64 text.
- `testing.WorkflowReplayer` no longer waits forever on a history with no workflow task yet, such as a cron run waiting for its next fire or a run started with `start_delay`: it replays cleanly, since no workflow code has run.
- `Client.updateWithStartWorkflow` now logs the server's message and status code when update-with-start fails with every operation marked aborted; it returned `error.RpcFailed` without logging why.
- Canceling a workflow coroutine that waits in `std.Io.Future.await` or `std.Io.Group.await` now passes the cancellation on to the awaited coroutines, as `std.Io` specifies; before, `Future.await` ignored it and `Group.await` returned `error.Canceled` while the members kept running.
- A workflow coroutine waiting to lock a `std.Io.Mutex` no longer blocks forever when the waiter ahead of it is woken by the unlock and canceled before it runs: that waiter still gets `error.Canceled`, and the wake passes on to the next waiter. The same holds for any single-waiter futex wake in workflow code.
